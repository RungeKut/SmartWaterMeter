## 1. Архитектура

```
┌─────────────────────────────────────────────────────┐
│                    ESP8266                           │
│  ┌─────────────┐  ┌──────────────┐  ┌────────────┐ │
│  │ DS18B20 x4  │  │  Счётчики x2 │  │  WiFi STA  │ │
│  │ (1-Wire)    │  │  (геркон,    │  │  / AP      │ │
│  │ GPIO0       │  │  прерывания) │  │            │ │
│  └──────┬──────┘  │ GPIO12,14    │  └──────┬─────┘ │
│         │         └──────┬───────┘         │       │
│         ▼                ▼                  ▼       │
│  ┌─────────────────────────────────────────────┐    │
│  │               Wemos_Mini.ino                │    │
│  │  (основной цикл: sensor → ws → broadcast)   │    │
│  └──────────┬──────────────────┬───────────────┘    │
│             │                  │                      │
│  ┌──────────▼────┐   ┌────────▼───────────┐         │
│  │ LittleFS      │   │ ESPAsyncWebServer   │         │
│  │ (SPA фронт)   │   │ + WebSocket (TCP)   │         │
│  └───────────────┘   └────────┬────────────┘         │
│                               │                        │
└───────────────────────────────┼────────────────────────┘
                               │
                        ┌──────▼──────┐
                        │  Браузер    │
                        │  (SPA, MD)  │
                        └─────────────┘
```

- **Веб-сервер:** ESPAsyncWebServer — асинхронный, не блокирует `loop()`
- **Фронтенд:** LittleFS — SPA на Material Design, одна HTML-страница
- **Обмен данными:** WebSocket + ArduinoJson 7.x
- **Среда:** PlatformIO, ESP8266 Arduino framework

## 2. Аппаратное обеспечение

| Компонент | Пин | GPIO | Примечание |
|-----------|-----|------|------------|
| DS18B20 Data | D3 | GPIO0 | 1-Wire шина (4 датчика) |
| Счётчик ГВС (импульсы) | D5 | GPIO14 | Прерывание CHANGE, INPUT_PULLUP |
| Счётчик ХВС (импульсы) | D6 | GPIO12 | Прерывание CHANGE, INPUT_PULLUP |
| Встроенный LED | D4 | GPIO2 | Активный LOW (LED_ON = LOW) |

**Плата:** Wemos D1 mini (ESP8266EX, 80MHz, 80KB RAM, 4MB Flash)

**Разметка flash:** `eagle.flash.4m2m.ld` — два OTA-слота по 1MB, файловая система 1MB, EEPROM 4KB.

### Датчики температуры

4 датчика DS18B20 на одной шине 1-Wire, маппинг каналов:

| Индекс | Имя | Назначение |
|--------|-----|------------|
| 0 | Cold | ХВС (холодная вода) |
| 1 | Hot | ГВС (горячая вода) |
| 2 | Return | Обратка отопления |
| 3 | Supply | Подача отопления |

### Счётчики воды

Герконовые счётчики с антидребезгом (20ms). Коэффициент `litersPerPulse` настраивается в веб-интерфейсе (по умолчанию 1.0 л/имп = 1000 imp/m³).

## 3. Модули прошивки

### 3.1. Wemos_Mini.ino

Главный файл, содержит `setup()`, `loop()`, WebSocket-обработчики, HTTP-маршруты, SMTP.

#### `setup()`
1. Инициализация последовательного порта (115200 бод)
2. LED (короткие 3 вспышки при старте)
3. Формирование имени устройства по MAC (`SmartWaterMeter-XXXXXX`)
4. Загрузка конфигурации из EEPROM (`ConfigStore::begin()`)
5. Инициализация датчиков DS18B20 (`TemperatureSensors::begin()`)
6. Инициализация счётчиков воды (`MeterCounter::begin()`)
7. Подключение к WiFi или переход в AP-режим
8. OTA (ArduinoOTA), Telnet, FailsafeOTA
9. Монтирование LittleFS и настройка WebSocket + HTTP-роутов

#### `loop()`

Основные задачи, выполняемые в порядке вызова:

| Задача | Период | Описание |
|--------|--------|----------|
| LED tick | каждый цикл | Обновление состояния LED |
| ArduinoOTA.handle | каждый цикл | OTA-обновления |
| Telnet.handle | каждый цикл | Обслуживание Telnet-клиентов |
| FailsafeOTA.handle | каждый цикл | Проверка таймаута подтверждения прошивки |
| WiFiupd | каждый цикл | Поддержание WiFi/AP |
| updateLocalTime | каждый цикл | Обновление локального времени из NTP |
| LED mode selection | каждый цикл | Выбор режима LED по состоянию системы |
| DS18B20 фаза 1 | каждые 5000 (1000 при калибровке) мс | `startConversion()` — запуск конверсии |
| DS18B20 фаза 2 | через 850мс после фазы 1 | `readTemperatures()` + broadcast |
| Рескан шины | каждые 30 секунд | `rescanBusLight()` — только `_allAddrs[]` |
| MeterCounter::flush | каждый цикл | Атомарный сбор импульсов со счётчиков |
| EEPROM save | каждые 5 минут | Сохранение показаний счётчиков и конфигурации |
| Email report | по расписанию | Отправка ежедневного/еженедельного/ежемесячного отчёта |

### 3.2. TemperatureSensors.h

Управление 4 датчиками DS18B20 на шине 1-Wire.

#### Поля класса

| Поле | Тип | Описание |
|------|-----|----------|
| `_expectedAddrs[4]` | `DeviceAddress[4]` | Ожидаемые адреса датчиков (из EEPROM или secrets.h) |
| `_temperatures[4]` | `float[4]` | Последние прочитанные температуры |
| `_found[4]` | `bool[4]` | Флаг «датчик обнаружен на шине» |
| `_allAddrs[16]` | `DeviceAddress[16]` | Все устройства на шине (для таблицы калибровки) |
| `_allAddrsCount` | `uint8_t` | Количество устройств на шине |
| `_deviceCount` | `uint8_t` | Количество датчиков (из DallasTemperature) |
| `_calibrating` | `bool` | Флаг активной калибровки |
| `_calibrateIndex` | `int` | Индекс калибруемого датчика (0-3) |
| `_calibrateBaseTemp[16]` | `float[16]` | Базовые температуры датчиков при старте калибровки |
| `_calibrateStartTime` | `uint32_t` | Время старта калибровки (ms) |
| `_config` | `ConfigStore*` | Указатель на конфигурацию (для сохранения адресов) |

#### Методы

| Метод | Описание |
|-------|----------|
| `begin()` | Инициализация DallasTemperature, сканирование шины, загрузка адресов из EEPROM/secrets.h, заполнение `_found[]` **и `_allAddrs[]`** |
| `rescanBus()` | Полное пересканирование шины: сброс `_found[]`, поиск всех устройств OneWire, перемаппинг. **Только для старта калибровки.** |
| `rescanBusLight()` | Лёгкое пересканирование: обновляет только `_allAddrs[]` для таблицы шины в веб-интерфейсе. **Не трогает `_found[]` и `_expectedAddrs`.** Вызывается автоматически каждые 30 секунд. |
| `startConversion()` | Асинхронный запуск конверсии (`requestTemperatures()`). Не блокирует. |
| `readTemperatures()` | Чтение результатов конверсии. Должен вызываться через ≥850 мс после `startConversion()`. |
| `requestTemperatures()` | Блокирующая обёртка: `startConversion()` + `delay(750)` + `readTemperatures()` |
| `getTemp(index)` | Получить температуру датчика (0-3) |
| `isFound(index)` | Проверить, найден ли датчик |
| `getTempHVS()` / `getTempGVS()` / `getTempReturn()` / `getTempSupply()` | Удобные методы для каждого канала |
| `getDeviceCount()` | Количество датчиков на шине |
| `startCalibration(index, cb)` | Запуск калибровки. Фиксирует базовые температуры всех датчиков на шине. |
| `cancelCalibration()` | Отмена калибровки |
| `isCalibrating()` | Проверка, активна ли калибровка |
| `getAllAddrCount()` | Количество устройств в `_allAddrs[]` (для таблицы шины) |
| `getAllAddr(i)` | Адрес устройства `i` в `_allAddrs[]` |
| `getRawTemp(busIndex)` | "Сырая" температура устройства по индексу шины (без маппинга) |
| `getCalibrateBaseTemp(busIndex)` | Базовая температура при старте калибровки |
| `getCalibrateDelta(busIndex)` | Дельта температуры относительно базовой |
| `getAddrSuffix(index)` | Последние 2 байта адреса датчика (hex) |
| `refreshAddrList()` | Синоним для `rescanBus()` |
| `sensorName(index)` | Статический метод: имя датчика по индексу ("Cold", "Hot", "Return", "Supply") |
| `formatTemp(temp)` | Статический метод: форматирование температуры (1 знак после запятой или "N/D") |

#### Загрузка адресов (`loadExpectedAddrs()`)

1. Проверяется EEPROM: если для датчика `i` записан ненулевой адрес — используется он
2. Если EEPROM пуст — используется `SENSOR_ADDR[i]` из `secrets.h`
3. Если адрес из EEPROM не найден на шине — пробуется `SENSOR_ADDR[i]` как fallback
4. При успешном fallback — новые адреса сохраняются обратно в EEPROM

#### Асинхронный цикл конверсии

```cpp
// Фаза 1 (каждые 5000 мс, 1000 мс при калибровке)
tempSensors.startConversion();   // ~10ms, запускает ~750ms конверсию на шине

// Фаза 2 (через ≥850 мс после фазы 1)
tempSensors.readTemperatures();  // ~50ms, читает результаты
```

Такой двухфазный подход гарантирует, что `loop()` не блокируется на 750мс, и WiFi/WebServer/WebSocket остаются отзывчивыми.

#### Калибровка

1. Пользователь выбирает канал (Cold/Hot/Return/Supply) в веб-интерфейсе
2. Запускается `startCalibration(index)`:
   - Фиксируются базовые температуры всех датчиков на шине
   - Запускается таймер на 60 секунд (`CALIBRATE_TIMEOUT`)
   - Интервал опроса сокращается до 1000 мс
3. Пользователь нагревает нужный датчик
4. При превышении порога `CALIBRATE_THRESHOLD` (5°C) — адрес сохраняется
5. Если таймаут — калибровка считается неудачной

### 3.3. MeterCounter.h

Счётчик импульсов с геркона (водосчётчик) на прерываниях.

#### Поля класса

| Поле | Тип | Описание |
|------|-----|----------|
| `_pulseCount` | `volatile uint32_t` | Накопленные импульсы (изменяется в прерывании) |
| `_waitingForRelease` | `volatile bool` | Флаг ожидания размыкания геркона |
| `_lastChangeMicros` | `volatile uint32_t` | Время последнего изменения (микросекунды) |
| `_debounceInterval` | `uint32_t` | Интервал антидребезга (20000 = 20ms) |
| `_isHot` | `bool` | true = ГВС, false = ХВС |
| `_store` | `ConfigStore*` | Для сохранения показаний |

#### Методы

| Метод | Описание |
|-------|----------|
| `begin(pin, isHot, store)` | Инициализация пина, установка прерывания |
| `flush()` | Атомарный сбор импульсов из прерывания, обновление `_store->data.meterHotM3`/`meterColdM3`. **Не пишет в EEPROM.** |
| `getPulseCount()` | Текущее количество неподтверждённых импульсов |
| `resetPulseCount()` | Сброс счётчика импульсов |

#### Алгоритм антидребезга

```
CHANGE → check debounce (20ms) → if FALLING && !waitingForRelease → pulse++ + waitingForRelease=true
                               → if RISING → waitingForRelease = false
```

Дополнительная защита: если при старте пин уже LOW — счётчик ждёт RISING перед подсчётом следующего импульса.

#### Важно: EEPROM и износ

`MeterCounter::flush()` обновляет значения только в RAM. Сохранение в EEPROM происходит раз в 5 минут в `loop()` через `ConfigStore::saveMeters()`. Это предотвращает износ EEPROM (ограничение ~100000 циклов записи).

### 3.7. FailsafeOTA.h

Безопасное OTA-обновление с автоматическим откатом (A/B слоты).

#### Механизм работы

1. После OTA прошивка загружается в неактивный слот (A: 0x10000, B: 0x101000)
2. ESP8266 перезагружается в новый слот
3. При старте пишется флаг "ожидание подтверждения" в RTC memory
4. Запускается таймер на 5 минут
5. Если пользователь подтвердил (веб-интерфейс или Telnet `confirm`) — флаг снимается
6. Если подтверждения нет 5 минут — ESP8266 переключается обратно на старый слот и перезагружается

#### Методы

| Метод | Описание |
|-------|----------|
| `begin()` | Инициализация: проверка RTC-флага, определение текущего слота |
| `handle()` | Вызов в `loop()` — проверка таймаута подтверждения |
| `confirm()` | Подтверждение новой прошивки |
| `isPending()` | Флаг ожидания подтверждения |
| `remainingSec()` | Секунд до отката |
| `getSlot()` | Номер текущего слота (0 или 1) |

#### Защита от циклической перезагрузки

Если устройство перезагружается 3 раза без подтверждения — FailsafeOTA автоматически откатывается, предотвращая bootloop.

## 4. Веб-интерфейс (SPA)

## 6. Калибровка датчиков DS18B20

Калибровка позволяет привязать физический датчик DS18B20 к логическому каналу (Cold/Hot/Return/Supply) без редактирования `secrets.h`.

### Процесс

1. Подключите **один** датчик, который будете калибровать
2. Перейдите на вкладку **Calibrate** в веб-интерфейсе
3. Убедитесь, что датчик отображается в таблице **Bus Sensors** (если нет — подождите до 30 секунд, либо подключитесь заново к странице — список обновится)
4. Нажмите **Calibrate** на нужном канале
5. Нагрейте физический датчик (пальцем, феном и т.п.)
6. Когда разница температуры превысит 5°C — адрес сохранится автоматически
7. Повторите для остальных датчиков (только по одному за раз!)

### Порог

`CALIBRATE_THRESHOLD = 5.0°C` — минимальное повышение температуры для фиксации адреса.

### Таймаут

`CALIBRATE_TIMEOUT = 60000 мс` (60 секунд) — если за это время датчик не нагреется на 5°C, калибровка отменяется.

### LED-индикация

Во время калибровки встроенный LED горит постоянно.

## 7. Особенности и подводные камни

### 7.1. Обновление списка датчиков на шине

**Проблема:** Массив `_allAddrs[]`, который отображается в таблице **Bus Sensors** на вкладке Calibrate, изначально заполнялся только один раз — в методе `begin()`. При подключении или отключении датчика таблица не обновлялась.

**Решение:** Добавлен метод `rescanBusLight()`, который безопасно пересканирует шину 1-Wire, обновляя только `_allAddrs[]`. Он вызывается в `loop()` каждые 30 секунд, сразу после `readTemperatures()`, когда шина свободна и конверсия не выполняется.

Отличие `rescanBusLight()` от `rescanBus()`:
- `rescanBusLight()` **не трогает** `_found[]` и `_expectedAddrs` — маппинг каналов не сбрасывается
- `rescanBusLight()` **не сбрасывает** `_deviceCount` из DallasTemperature
- `rescanBusLight()` выводит в Serial только количество найденных устройств (без детального лога)

**Когда таблица шины обновляется:**
1. При подключении WebSocket-клиента (первый `fullState`)
2. Каждые ~5 секунд вместе с данными `sensors`
3. После каждого рескана шины (каждые 30 секунд)

**Задержка:** при подключении/отключении датчика изменения отобразятся в течение 30 секунд (максимум). При перезагрузке устройства — сразу.

### 7.2. Асинхронный цикл DS18B20

Одна из основных причин прошлых сбоев (watchdog reset). Двухфазный цикл:
- Фаза 1: `startConversion()` — только запускает конверсию
- Фаза 2: `readTemperatures()` — читает результат через ≥850 мс

Нельзя вызывать `startConversion()` повторно до завершения предыдущей конверсии. Флаг `sensorConvPending` в `loop()` гарантирует это.

### 7.3. OneWire и watchdog

Каждое обращение к OneWire — блокирующая операция. `rescanBus()` (~5-10 мс) безопасен, но при слишком частом вызове (каждые 1000 мс) может привести к watchdog reset. Поэтому:
- `rescanBusLight()` вызывается не чаще чем раз в 30 секунд
- Во время калибровки рескан шины отключается

### 7.4. EEPROM и износ

`MeterCounter::flush()` не пишет в EEPROM — только обновляет значения в RAM. EEPROM сохраняется раз в 5 минут в `loop()`, объединяя показания счётчиков и конфигурацию в одну операцию записи. Это продлевает срок службы EEPROM (~100000 циклов записи).

### 7.5. Инициализация счётчиков при старте

Если при включении питания геркон счётчика уже замкнут (пин LOW), `MeterCounter` ждёт размыкания (RISING) перед подсчётом первого импульса. Это предотвращает ложный импульс при старте.

### 7.6. Безопасность

- Telnet — без пароля (только доверенная сеть)
- Точка доступа — открытая (пароль настраивается в `secrets.h`)
- Все данные передаются в открытом виде (HTTP, WebSocket без WSS, Telnet)
- `secrets.h` исключён из git (в `.gitignore`)

### 7.7. Адресация

- AP-режим: `192.168.0.1/24`
- В коде не должно быть упоминаний `192.168.4.1` — это адрес по умолчанию для ESP8266 SoftAP, но в проекте намеренно изменён на `192.168.0.1` из-за конфликтов в сети.

## 8. Сборка и прошивка

### Требования

- PlatformIO (VS Code с расширением PlatformIO или `pip install platformio`)
- USB-кабель (Wemos D1 mini)

### Первая прошивка (USB)

```bash
# Сборка
pio run

# Заливка прошивки
pio run --target upload --upload-port COM3

# Заливка файловой системы (LittleFS) с SPA фронтендом
pio run --target uploadfs --upload-port COM3
```

### OTA-обновление (после первой прошивки)

```bash
# Собрать и залить через WiFi
pio run --target upload --upload-port 192.168.x.x

# Файловую систему тоже можно по WiFi
pio run --target uploadfs --upload-port 192.168.x.x
```

### Первый запуск

1. Подключитесь к точке доступа `SmartWaterMeter-XXXXXX` (открытая)
2. Откройте `http://192.168.0.1`
3. В настройках укажите SSID и пароль WiFi
4. Настройте SMTP при необходимости
5. Откалибруйте датчики температуры
