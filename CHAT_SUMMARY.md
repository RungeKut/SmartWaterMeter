## Последние изменения

### [18] feat: адреса датчиков в интерфейсе, живой признак присутствия (12.09.2026)

**Адрес рядом с каналом.** В карточке Calibration под температурой показан адрес закреплённого датчика — **в том числе для отсутствующего**, чтобы его можно было найти и подключить. В `sensorMapping` добавлены поля `address` и `assigned`.

Три состояния канала:

| Бейдж | Что значит |
|---|---|
| **Found** | Адрес закреплён, датчик читается |
| **Missing** | Адрес закреплён, датчик не отвечает. Адрес показан |
| **Not assigned** | За каналом нет адреса |

Признак `assigned` проверяет CRC адреса — это отсекает заглушки `{0x28, 0, 0, ...}` из `secrets.h`, которые адресом не являются.

**Связь канала с шиной.** В таблице Bus Sensors рядом с адресом показан чип с именем канала, за которым датчик закреплён. При наведении мыши обе строки с одинаковым адресом подсвечиваются рамкой. Таблицы перерисовываются раз в секунду, поэтому подсветка хранится в переменной и применяется заново после каждой отрисовки.

**Признак присутствия стал живым.** Раньше `_found[]` выставлялся один раз в `begin()`: подключённый на ходу датчик оставался Missing до перезагрузки, а отключённый продолжал числиться Found. То есть ровно тот сценарий, ради которого адрес и понадобилось показывать, не работал.

**Попутно вскрылась тонкость, стоившая двух итераций.** Сначала я привязал присутствие к поиску по шине — и канал Cold стал числиться Missing в 92 замерах из 98, показывая при этом корректные 27°C.

Причина: `getAddress()` выполняет живой поиск по шине, и подвисающий датчик в него попадает через раз. На **прямой** запрос по адресу (MatchROM) тот же датчик отвечает нормально. В прежнем коде был запасной путь с прямым чтением, и при перестройке я его убрал.

Итоговая логика: адрес есть в списке шины → берём из кеша; нет → прямой запрос с повтором; `Missing` только после `MAX_READ_FAILURES` неудач подряд.

**Проверено на устройстве** (прошито по OTA):

| Проверка | Результат |
|---|---|
| Адреса всех 4 каналов | отдаются, совпадают с устройствами на шине |
| Стабильность признака found | 0 смен за 97 замеров, 3+ цикла рескана |
| Missing по каналам | 0 из 97 по всем четырём |
| Разметка SPA | все новые элементы отдаются устройством |

**Сборка:** SUCCESS, RAM 54.1% (44292 байт), Flash 62.8% (655992 байт).

### [17] feat: ручное назначение датчиков при калибровке, таймаут 5 минут (12.09.2026)

**Таймаут калибровки** увеличен с 60 секунд до 5 минут (`CALIBRATE_TIMEOUT`). В статусе калибровки появился обратный отсчёт — при пятиминутном окне без него непонятно, сколько времени осталось.

**Кнопки «+» в таблице Bus Sensors.** Появляются только во время калибровки и назначают датчик тому каналу, для которого она запущена, — без нагрева. Выручает, когда датчик недоступен физически или нагреть его на 5°C затруднительно.

Новое сообщение WebSocket: `{"type":"assignSensor","index":<канал>,"busIndex":<индекс>}`, ответ `assignResult`.

**Дубликаты не допускаются.** Если выбранный датчик уже закреплён за другим каналом, тот канал освобождается, и в уведомлении сказано, за каким. Иначе `findMapping()` вернул бы для одного адреса только младший канал, и второй после перезагрузки молча стал бы Missing.

Назначение сразу сохраняется в EEPROM и, если для этого канала шла калибровка, завершает её успехом.

**Проверено на устройстве** (прошито по OTA, файловая система тоже):

| Проверка | Результат |
|---|---|
| Запуск калибровки | `calibrate_remaining` = 299 сек, отсчёт идёт |
| Назначение свободного датчика | `Cold assigned`, калибровка завершена успехом |
| Назначение занятого датчика | `Return assigned, Cold released`, Cold стал Missing |
| Восстановление сопоставления | Cold/Hot/Return/Supply вернулись к исходным датчикам |

Исходное сопоставление (Cold=bus0, Hot=bus1, Return=bus2, Supply=bus3) после тестов восстановлено.

**Сборка:** SUCCESS, RAM 54.0% (44252 байт), Flash 62.8% (655520 байт).

### [16] fix: переписан подсчёт герконовых импульсов (11.09.2026)

**Что было сломано.** Старый ISR при срабатывании антидребезга делал `return`, не записав время и не обновив состояние:

```cpp
if (now - _lastChangeMicros < _debounceInterval) return;   // фронт потерян
```

Короткое замыкание теряло свой размыкающий фронт, флаг `_waitingForRelease` залипал в `true` — и **все последующие импульсы молча пропадали**, пока не случалось замыкание длиннее 20 мс. На медленных импульсах ломалось с другой стороны: фронты дребезга расходились дальше 20 мс, флаг переключался туда-сюда, и один литр считался несколько раз.

**Новая архитектура (вариант A):** захват в ISR, разбор в `loop()`.

- ISR только кладёт `(время, уровень)` в кольцевой буфер на 16 событий. Ни один фронт не теряется, даже когда `loop()` занят чтением датчиков на ~100 мс
- Автомат с гистерезисом по времени работает в `process()`: замыкание подтверждается при LOW ≥ `debounceClosedMs` (5 мс), размыкание при HIGH ≥ `debounceOpenMs` (50 мс)
- Самокоррекция: после разбора очереди состояние сверяется с реальным уровнем пина, поэтому переполнение буфера не уводит автомат в рассинхрон

**Импульс засчитывается по завершению замкнутой фазы, а не в её начале.** Это снимает неоднозначность при пропадании питания: если плата выключилась с замкнутым герконом, прошлая прошивка импульс засчитать не могла, значит после включения его можно смело учесть при размыкании. Ни двойного счёта, ни пропуска.

**Залипший на месяцы геркон.** Опасно не само залипание (стабильное состояние), а микродребезг в нём — его отсекает `debounceOpenMs`. Возраст состояния считается в секундах, а не через `micros()`/`millis()`, которые переполняются через 71 минуту и 49 дней.

**Запись в EEPROM — через 30 секунд после последнего импульса.** Расход идёт пачками, поэтому теряется только то, что пришлось на обрыв питания прямо во время водоразбора, а число записей равно числу «сеансов» за сутки. Периодическое сохранение раз в 5 минут осталось подстраховкой для конфигурации.

**Настраиваемые пороги.** `debounceClosedMs` / `debounceOpenMs` в EEPROM, правятся в Settings → Reed Debounce, `0` = значения по умолчанию. Заняли 4 байта из резерва — размер `ConfigData` не изменился, настройки на устройстве уцелели (проверено: SSID и показания после прошивки на месте).

**Диагностика** в Settings → Reed Diagnostics: состояние геркона и его возраст, число импульсов, длительности замыканий (последняя / мин / макс), счётчик дребезга и потерянных событий. Замкнут дольше суток — подсветка красным. Данные приходят в `fullState` (раз в 30 с), в секундную рассылку не кладутся.

**Проверено на устройстве** (прошито по OTA, файловая система тоже по WiFi):

```
[Meter] Hot on pin 14: open at boot, debounce 5/50 ms
[Meter] Cold on pin 12: open at boot, debounce 5/50 ms
```

Диагностика отдаётся, возраст состояния тикает корректно, фантомных импульсов за время наблюдения нет (pulses=0, bounces=0, overflow=0), heap 19568.

> **Не проверено:** реальный подсчёт при водоразборе — нужен физический импульс с геркона. Первые цифры в Reed Diagnostics покажут фактические длительности замыканий ваших счётчиков; по ним и стоит подобрать пороги.

> **При переходе со старой прошивки** возможен один лишний импульс, если обновление пришлось ровно на замкнутую фазу: старая версия считала в начале замыкания, новая — в конце. Разовая погрешность в 1 литр.

**Сборка:** SUCCESS, RAM 53.8% (44060 байт), Flash 62.6% (654240 байт).

### [15] feat: опрос датчиков раз в секунду (11.09.2026)

**Запрос:** можно ли обновлять показания раз в секунду. Можно — но сначала пришлось убрать то, что мешало.

**Асинхронный цикл не был асинхронным.** Проект не вызывал `setWaitForConversion(false)`, а в DallasTemperature по умолчанию `waitForConversion = true`. Поэтому `startConversion()` не запускал конверсию, а дожидался её в `yield()`-цикле ~750 мс. Двухфазная схема с ожиданием 850 мс просто добавляла простой сверху: `loop()` стоял ~880 мс из каждых 2000.

**Кеш температур шины.** `getRawTemp()` при каждом вызове читал датчик с шины заново. При 8 устройствах одна рассылка стоила ~90 мс блокировки, при калибровке вдвое больше. Теперь `readTemperatures()` обходит шину один раз за цикл, геттеры читают кеш.

После этого `sensorInterval` снижен с 2000 до 1000 мс. Цикл ~1010 мс, `loop()` занят ~100 мс из них.

**Побочная находка: один датчик на шине физически сбоит.** Канал Cold начал показывать `N/D`. A/B-проверка на устройстве по 45 замеров:

| Интервал | Сбои Cold | Остальные 7 |
|---|---|---|
| 1000 мс | 18 из 45 (40%) | 0 |
| 2000 мс | 13 из 45 (29%) | 0 |

Разница незначима — дело в самом датчике `28E0A43D000000CE`, а не в частоте. Добавлены одна повторная попытка чтения при сбое CRC и терпимость к 3 сбоям подряд с удержанием последнего валидного значения.

**Проверено на устройстве (прошито по OTA, подтверждено):**

| Показатель | Значение |
|---|---|
| Интервал рассылки | 1002-1030 мс (замер по 45 сообщениям) |
| Сбои чтения | 0 из 45 по всем четырём каналам |
| Free heap | стабильно 19912, минимум 16032 в пике |
| Утечек | нет: первый и последний замеры совпадают |

### [14] fix: OTA никогда не применялся — флаг RTC затирал команду загрузчика (11.09.2026)

**Обнаружено при попытке прошить устройство по WiFi.**

`espota` отрапортовал `Result: OK`, плата перезагрузилась — но осталась на старой прошивке. Диагноз по Telnet-баннеру: дата сборки `Sep 9 2026 23:48:04`, в `help` нет команды `confirm`.

**Причина.** Пользовательская RTC-память ESP8266 — 512 байт, но первые 128 байт занимает команда загрузчика `eboot`, которую пишет `Updater::end()`. Цитата из ядра (`cores/esp8266/Esp.cpp`):

> *the eboot command will be stored into the first 128 bytes of user data... That means that user data present there will be lost*

Порядок в `ArduinoOTA::_runUpdate()` (`ArduinoOTA.cpp:315-333`):
1. `Update.end()` → пишет команду eboot `ACTION_COPY_RAW`
2. `_end_callback()` → `failsafe.updateFirmware()` → `rtcUserMemoryWrite(0, 0xDEAD0001)` — **затирает поле `magic` команды**
3. `ESP.restart()`

Загрузчик не находит валидной команды, образ из временной области не копируется в `0x00000`, плата поднимается на старой прошивке. Протокол OTA при этом отрабатывает штатно и рапортует успех.

**Следствие:** записи [11] и [12] о «успешном OTA» описывали передачу файла, а не применение прошивки. Устройство всё это время работало со сборкой от 9 сентября.

**Исправление:** `RTC_FLAG_OFFSET = 32` (байт 128) — флаг вынесен за пределы области eboot.

**Важно: это исправление нельзя доставить по воздуху.** Прошивка с багом при каждой попытке OTA снова затирает команду загрузчика. Нужна **одна прошивка по USB**:

```bash
pio run --target upload --upload-port COM3
pio run --target uploadfs --upload-port COM3
```

После неё OTA заработает нормально.

> Обновление файловой системы (`uploadfs`) багом не затронуто: без `ATOMIC_FS_UPDATE` образ LittleFS пишется напрямую, команда eboot не используется.

**Как проверять OTA впредь:** Telnet-баннер печатает `__DATE__ __TIME__` сборки. Не изменилась дата — образ не применился.

**Сборка:** SUCCESS, RAM 53.1% (43484 байт), Flash 62.5% (652348 байт).

### [13] fix: полный аудит проекта — 18 дефектов, документация приведена в соответствие (11.09.2026)

**Критичные ошибки:**

1. **Счётчики завышали показания в 1000 раз.** `MeterCounter::flush()` трактовал `litersPerPulse` как м³ на импульс, хотя поле подписано «литры» и в UI, и в `secrets.h`. Добавлено деление на 1000.
2. **Датчики за пределами первых четырёх не находились.** Циклы сопоставления в `begin()` и `loadExpectedAddrs()` были ограничены `i < NUM_SENSORS`. При 8 датчиках на шине исправный датчик показывал «Missing». Перебор идёт по `_allAddrsCount`.
3. **Мусорные дельты при калибровке** (`+536870900.0°`, `-1.5e+23°`). `loop()` вызывал `rescanBus()` *после* `startCalibration()`, и для новых индексов `_calibrateBaseTemp[]` оставался неинициализированным. Рескан перенесён внутрь `startCalibration()`, массив инициализируется целиком, добавлен флаг `_calibrateBaseReady`.
4. **Сохранение настроек стирало пароли.** Сервер не отдаёт пароли клиенту, поэтому поля в SPA всегда пустые — и любое сохранение записывало пустые строки. Добавлен `keepOrSet()`: пустое значение = «оставить как было».
5. **`rescanBus()` через сырой `_oneWire.search()`** нарушал собственное правило проекта (pitfalls §10) и ломал состояние DallasTemperature при каждом старте калибровки. Метод удалён.

**FailsafeOTA переписан** (решение принято после обсуждения):

Механизм A/B-слотов не соответствовал реальности — на ESP8266 их нет. `ArduinoOTA` пишет образ во временную область, а `eboot` при ребуте копирует его в `0x00000` поверх старого. Откатываться некуда.

- `getCurrentSlot()` всегда возвращал 1: маска `& 0x3FFFFF` по адресу в окне `0x402xxxxx` даёт значение заведомо больше `0x101000`
- `rollback()` писал `ACTION_LOAD_APP` на адрес, где образа не было
- Удалён `upload_script.py` — он шил прошивку в `0x10000`/`0x101000`, оставляя `0x0` пустым; плата бы не загрузилась

Осталось: флаг в RTC, баннер, `/confirm`, telnet `confirm`, одна перезагрузка по таймауту (вместо bootloop).

**Telnet реально начал показывать логи.** Хук `os_install_putc1()` перехватывал только вывод SDK, а `Serial.printf` шёл в UART мимо него — логи прошивки в Telnet не попадали никогда. Вдобавок предыдущий обработчик не сохранялся, и вывод SDK пропадал из USB-Serial. Добавлен `src/Log.h`: `Logger : public Print` пишет в Serial и в зарегистрированный приёмник. Весь проект переведён с `Serial.*` на `Log.*`.

## Инструкция по прошивке

### USB

```bash
pio run --target upload --upload-port COM3
pio run --target uploadfs --upload-port COM3   # если менялся index.html
```

### OTA (через WiFi)

```bash
pio run --target upload
```

> **Важно:** Хост и ESP должны быть в одной сети. На хосте должен быть открыт TCP-порт 33777 (входящие) в Windows Firewall. Если OTA не работает:
> 1. Проверьте `upload_flags --host_ip` в `platformio.ini` — должен быть актуальный IP хоста
> 2. Проверьте правило FW: `netsh advfirewall firewall show rule name="PlatformIO OTA 33777"`
> 3. Если правило отсутствует: `netsh advfirewall firewall add rule name="PlatformIO OTA 33777" dir=in action=allow protocol=TCP localport=33777`

### Первый запуск после USB

1. Плата загрузится с новым FailsafeOTA
2. Если **не было OTA** — баннер подтверждения НЕ появляется, всё работает сразу
3. Если был OTA — открой `http://192.168.88.87/confirm` в браузере или нажми Confirm на баннере
