# Тесты на хосте

Два независимых набора, оба гоняются на компьютере — без платы, без прошивки, за секунды.

| Набор | Что проверяет | Запуск |
|-------|---------------|--------|
| `test/` | Логика прошивки на C++ (Unity) | `pio test -e native` |
| `tests/` | Логика SPA на JavaScript (Node) | `node tests/run.js` |

## Зачем

Половина дефектов этого проекта — тихие: прошивка работает, ничего не падает, но данные неверны. Счётчики завышали показания в 1000 раз почти год. Месячное расписание отчётов сбрасывалось при каждом открытии страницы. Полночь нельзя было выставить.

Ни один из них не проявляется в виде ошибки. Все три ловятся тестом за полторы секунды.

Проверять такое на плате дорого: нужен физический импульс с геркона, реальное наступление нужной даты, браузер. На хосте время и уровни пинов задаёт сам тест.

## C++: логика прошивки

```bash
pio test -e native
```

### Как это устроено

Модули проекта header-only и завязаны на Arduino. Чтобы собрать их обычным компилятором, в `test/stubs/` лежат заглушки, подменяющие железозависимые заголовки:

| Заглушка | Что даёт |
|----------|----------|
| `Arduino.h` | Типы, `pinMode`/`digitalRead`, `Print`, и главное — **управляемое тестом время**: `micros()`/`millis()` читают переменную, которую двигает `advanceMillis()` |
| `EEPROM.h` | Массив вместо flash. Как и ядро ESP8266, `put()` сравнивает содержимое, а `commit()` без изменений ничего не делает |
| `secrets.h` | Значения для тестов. Настоящий `secrets.h` в `.gitignore`, поэтому тесты используют свой |

Порядок включения важен: `-I test/stubs` идёт первым, поэтому заглушки перекрывают настоящие заголовки.

### Что покрыто

`test/test_meter/` — автомат подсчёта импульсов геркона, самая тонкая логика в проекте:

- нормальный импульс, серия импульсов
- **короткий импульс не ломает счётчик** — прежняя реализация после него замолкала навсегда
- замыкание короче порога игнорируется
- дребезг на замыкании не даёт лишних импульсов
- микродребезг в залипшем положении не накручивает счётчик
- возраст состояния растёт при залипании
- **замкнутый геркон при старте** даёт ровно один импульс при размыкании
- **литры → м³**: 10 импульсов по 1 литру дают 0.010 м³, а не 10
- цена импульса 10 литров
- две фазы без достаточной паузы не считаются дважды
- диагностика длительности замыкания

### Проверка, что тесты действительно ловят баги

Верните в `MeterCounter::process()` старую ошибку:

```cpp
float totalM3 = count * litersPerPulse;   // без / 1000.0f
```

```
test_liters_to_cubic_meters: Expected 0.01 Was 10   [FAILED]
test_liters_per_pulse_ten:   Expected 0.1  Was 100  [FAILED]
```

## JavaScript: логика SPA

```bash
node tests/run.js
```

Зависимостей нет — нужен только Node. Ни `npm install`, ни `package.json`: ради двух десятков проверок тянуть jest в встраиваемый проект несоразмерно.

### Как это устроено

`tests/frontend/harness.js` вырезает блок `<script>` из `data/index.html` и выполняет его в изолированном контексте Node с подставным DOM.

Две тонкости, без которых ничего не работает:

**Селекты эмулируются по-настоящему.** Присваивание значения, которого нет среди `option`, игнорируется — как в браузере. Именно на этом ловится сброс месячного расписания.

**`state` и `schedMode` объявлены через `let`.** Они живут в лексической области скрипта, а не в объекте контекста, поэтому присвоить их снаружи через `ctx.state` нельзя — функции этого не увидят. Для этого есть `exec()`, выполняющий код внутри того же контекста.

### Что покрыто

`tests/frontend/schedule.test.js`:

- `nextReportDate()` — ежедневно, еженедельно, ежемесячно; переходы через конец месяца и года; полночь; отсутствие синхронизации времени
- round-trip «загрузили настройки → сохранили»: месячное расписание не теряет число, полночь сохраняется как 0, для ежедневного день принудительно обнуляется

`tests/frontend/markup.test.js`:

- скрипт синтаксически корректен
- все `getElementById` разрешаются в разметке
- нет обращений к удалённым элементам
- SPA не разросся сверх разумного

Последние два появились не случайно: правки SPA делались генерирующими скриптами, и сломанные строковые литералы с несуществующими id уже случались.

## Требования

**Node** — для тестов SPA. Обычно уже есть.

**Хостовый компилятор** — для C++. На машине, где велась разработка, его не было; поставили тулчейн средствами самого PlatformIO, без прав администратора:

```bash
pio pkg install -g -t platformio/toolchain-gccmingw32
```

После этого его каталог нужно добавить в `PATH` перед запуском тестов:

```bash
export PATH="$HOME/.platformio/packages/toolchain-gccmingw32/bin:$PATH"
pio test -e native
```

На Linux и macOS системного `g++` достаточно.

> `pio run` собирает только прошивку: в `[platformio]` задан `default_envs = d1_mini`. Без этого обычная сборка требовала бы хостового компилятора.
