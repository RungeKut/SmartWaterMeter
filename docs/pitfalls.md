# SmartWaterMeter — Особенности и подводные камни

## 1. Обновление списка датчиков на шине

**Проблема:** Массив `_allAddrs[]`, который отображается в таблице **Bus Sensors** на вкладке Calibrate, изначально заполнялся только один раз — в методе `begin()`. При подключении или отключении датчика таблица не обновлялась.

**Решение:** Добавлен метод `rescanBusLight()`, который пересканирует датчики на шине через штатный API DallasTemperature (`getDeviceCount()` + `getAddress()`). Вызывается в `loop()` каждые 30 секунд, сразу после `readTemperatures()`.

**Важно:** В первой версии `rescanBusLight()` использовал прямой вызов `_oneWire.search()`, что сбивало внутреннее состояние DallasTemperature. После рескана все датчики возвращали `DEVICE_DISCONNECTED_C`. Исправлено — теперь используется только DallasTemperature API.

**Свойства `rescanBusLight()`:**
- **не трогает** `_found[]` и `_expectedAddrs` — маппинг каналов не сбрасывается
- работает через DallasTemperature API — безопасен для конвейера конверсии
- выводит в лог только количество найденных устройств

Второй метод, `rescanBus()`, работавший через сырой `_oneWire.search()`, **удалён** — он нарушал правило из раздела 10 и ломал состояние DallasTemperature при каждом старте калибровки.

**Когда таблица шины обновляется:**
1. При подключении WebSocket-клиента (первый `fullState`)
2. Каждые ~2 секунды вместе с данными `sensors`
3. После каждого рескана шины (каждые 30 секунд)
4. При старте калибровки — рескан выполняется внутри `startCalibration()`

**Задержка:** при подключении/отключении датчика изменения отобразятся в течение 30 секунд (максимум). При перезагрузке устройства — сразу.

## 2. Асинхронный цикл DS18B20

Одна из основных причин прошлых сбоев (watchdog reset). Двухфазный цикл:
- Фаза 1: `startConversion()` — только запускает конверсию
- Фаза 2: `readTemperatures()` — читает результат через ≥850 мс

**Нельзя** вызывать `startConversion()` повторно до завершения предыдущей конверсии. Флаг `sensorConvPending` в `loop()` гарантирует это.

## 3. OneWire и watchdog

Каждое обращение к OneWire — блокирующая операция (~5-10 мс). При слишком частом вызове это приводит к watchdog reset. Поэтому:
- `rescanBusLight()` вызывается не чаще чем раз в 30 секунд
- Во время калибровки периодический рескан из `loop()` отключён
- Единственный рескан при калибровке — внутри `startCalibration()`, до снятия базовых температур

## 4. EEPROM и износ

Ограничение EEPROM ESP8266: ~100000 циклов записи.

`MeterCounter::flush()` не пишет в EEPROM — только обновляет значения в RAM. EEPROM сохраняется раз в 5 минут в `loop()`, объединяя показания счётчиков и конфигурацию в одну операцию записи.

**Дополнительной защиты не требуется.** `EEPROM.put()` в ядре ESP8266 сравнивает буфер с текущим содержимым (`memcmp`) и выставляет `_dirty` только при реальном отличии, а `commit()` при `!_dirty` выходит сразу, не трогая flash. То есть периодическое сохранение без изменений физически ничего не пишет.

> Раньше `loop()` вызывал подряд `config.saveMeters()` и `config.save()` — две одинаковые записи одной и той же структуры. `saveMeters()` удалён.

## 5. Инициализация счётчиков при старте

Если при включении питания геркон счётчика уже замкнут (пин LOW), `MeterCounter` ждёт размыкания (RISING) перед подсчётом первого импульса. Это предотвращает ложный импульс при старте.

## 6. Имя устройства

Формируется по последним 3 байтам MAC-адреса: `SmartWaterMeter-XXXXXX` (где X — hex от 3 байт MAC). Используется как hostname, SSID точки доступа, идентификатор в email.

## 7. Безопасность

- **Telnet** — без пароля (только доверенная сеть)
- **Точка доступа** — открытая (пароль настраивается в `secrets.h`, `AP_PASS_DEFAULT`)
- **Веб-интерфейс** — HTTP, без HTTPS
- **WebSocket** — без WSS
- **secrets.h** — исключён из git (в `.gitignore`)

## 8. WiFi: реконнект и AP-режим

- Попытки подключения к WiFi: каждые 30 секунд
- После 3 неудач — запуск AP-режима на `192.168.0.1/24`
- В AP-режиме — попытка реконнекта каждые 10 минут
- При успешном реконнекте — AP выключается

## 9. Адресация

- AP-режим: `192.168.0.1/24`
- В коде не должно быть упоминаний `192.168.4.1` — это адрес ESP8266 SoftAP по умолчанию

## 10. DallasTemperature: прямой доступ к OneWire ломает состояние

**Никогда** не вызывай `_oneWire.search()`, `_oneWire.reset_search()` или другие методы OneWire напрямую, если используется DallasTemperature. Это сбивает внутренний кеш адресов DallasTemperature.

**Симптом:** после прямого обращения к OneWire, `_sensors.getTempC()` начинает возвращать `DEVICE_DISCONNECTED_C` (`-127°C`) для всех датчиков.

**Решение:** всегда работай через API DallasTemperature: `_sensors.getAddress()`, `_sensors.getDeviceCount()`, `_sensors.requestTemperatures()`.

Это касается и `rescanBusLight()` — первая версия использовала прямой OneWire, что вызывало периодическое пропадание всех датчиков раз в 30 секунд.

## 11. Сохранность EEPROM (настроек) при перепрошивке

**Вопрос:** Пропадают ли настройки (WiFi, SMTP, калибровка) после `pio run --target upload`?

**Ответ:** Нет, если не делать полное стирание flash. Разметка `eagle.flash.4m2m.ld` (значения взяты из ld-скрипта, адреса CPU пересчитаны в смещения flash вычитанием `0x40200000`):

| Область | Адрес (flash) | Размер | Затирается при upload | Затирается при uploadfs |
|---------|---------------|--------|----------------------|------------------------|
| Прошивка | `0x000000` | ~1 MB | **Да** | Нет |
| Временная область OTA | под FS | по размеру образа | Нет | Нет |
| LittleFS (файлы) | `0x200000` | 2 MB | Нет | **Да** |
| EEPROM | `0x3FB000` | 4 KB | **Нет** | **Нет** |

EEPROM лежит на `0x3FB000` — физически отдельно от прошивки и файловой системы. При обычной прошивке esptool пишет в диапазон `0x000000..0x100000`, не трогая EEPROM.

> В прошлой версии этого документа указывался адрес `0x7FB000` — он соответствовал бы 8 МБ flash. У Wemos D1 mini флеш 4 МБ, и `_EEPROM_start` в `eagle.flash.4m2m.ld` равен `0x405fb000`, то есть смещение `0x3FB000`.

**Когда настройки могут ПОТЕРЯТЬСЯ:**

1. **`pio run --target erase` (явное стирание):** стирается весь чип, включая EEPROM.

2. **Изменение структуры `ConfigData`:** если поменять порядок или размер полей, старые данные будут прочитаны неверно. Магическое число `0x5A4B` от этого не спасает — оно проверяет только факт инициализации. При изменении структуры меняйте и `EEPROM_MAGIC`.

3. **Дёргание USB-кабеля во время записи EEPROM:** если плата потеряет питание в момент `ConfigStore::save()` — данные не допишутся, `magic` окажется повреждён, и ConfigStore сбросит настройки на defaults.

**Как защититься:**
- В `platformio.ini` уже стоит `board_upload.erase_cmd =` — это отключает полное стирание flash при upload
- Если настройки всё же сбросились — введите их заново в веб-интерфейсе и сохраните

> **Раньше здесь была неверная причина №1** — «FailsafeOTA откатился на старый слот». Никакого отката не происходило: A/B-слотов на ESP8266 нет (см. раздел 12). Если настройки терялись, дело было в одной из причин выше.

## 12. OTA: никакого отката не существует

Модуль `FailsafeOTA` раньше обещал A/B-слоты и автоматический откат. Этого механизма на ESP8266 нет.

**Как на самом деле работает OTA:**
1. `ArduinoOTA` пишет образ во временную область flash под файловой системой
2. `Updater::end()` записывает команду загрузчика `eboot`: `ACTION_COPY_RAW`
3. При перезагрузке `eboot` **копирует образ в `0x00000`** поверх старой прошивки

Старой прошивки после этого не существует — откатываться некуда.

**Почему откат невозможен в принципе:** команду `eboot` пишет работающее приложение. Прошивка, падающая до `loop()`, не может попросить откат. Закрыть этот сценарий может только собственный загрузчик, а он шьётся исключительно по USB.

**Что делает модуль сейчас:** подтверждение того, что новая прошивка дожила до `loop()`. Нет подтверждения за 5 минут → одна перезагрузка. После неё повторов нет — иначе получился бы bootloop.

Подробности и список удалённого кода — в [modules/ota.md](modules/ota.md).

## 13. Литры и кубометры в счётчиках

Коэффициент `litersPerPulse` задаётся **в литрах** (так подписано поле в веб-интерфейсе и в `secrets.h`), а показания хранятся в **м³**. Пересчёт обязателен:

```cpp
float totalM3 = (count * litersPerPulse) / 1000.0f;
```

**Что было:** деления не было, коэффициент трактовался как м³ на импульс. При значении по умолчанию `1.0` каждый литр воды добавлял к показаниям 1 м³ — завышение ровно в 1000 раз.

Если на устройстве уже накопились завышенные показания, введите правильные значения вручную в Settings → Meters.

## 14. Пароли не возвращаются клиенту

Сервер не отдаёт `wifiPass` и `smtpPass` в `fullState` — это правильно, но у этого есть следствие.

В SPA поля паролей всегда пустые. Если трактовать пустое значение как «сохранить пустую строку», то любое сохранение настроек (например, смена времени отчёта) стирало бы пароль WiFi, и после перезагрузки устройство уходило бы в AP-режим.

Поэтому `keepOrSet()` в `handleWsMessage` записывает пароль **только если поле непустое**. Чтобы сменить пароль — введите новый; чтобы оставить — не трогайте поле.

Стереть пароль через веб-интерфейс нельзя. Это сознательный компромисс: цена случайной потери связи с устройством выше.

## 15. Сопоставление датчиков ограничивалось четырьмя устройствами

Циклы поиска датчиков в `begin()` и `loadExpectedAddrs()` были ограничены `i < NUM_SENSORS`, то есть просматривали только первые 4 устройства на шине. При большем количестве датчиков (в проекте их бывает 8) нужный мог не найтись, и канал показывал «Missing» при исправном датчике.

Теперь перебор идёт по `_allAddrsCount` — по всем устройствам на шине.
