# MqttClient.h — MQTT и автодискавери Home Assistant

## Зачем, если уже есть `/api.json`

REST требует, чтобы Home Assistant опрашивал устройство и чтобы сущности были описаны руками в YAML. MQTT переворачивает схему: устройство само публикует данные в брокер и само себя описывает — сущности появляются в HA без единой строки конфигурации.

REST и `/metrics` при этом **остаются**: они не мешают, работают без брокера и удобны для отладки и Prometheus.

## Почему AsyncMqttClient, а не PubSubClient

`PubSubClient::connect()` блокирует `loop()` до таймаута сокета. Ровно на этом обжёгся NTPClient ([pitfalls §17](../pitfalls.md)): недоступный сервер — и устройство тормозит постоянно.

AsyncMqttClient работает поверх ESPAsyncTCP, который в проекте уже есть, и не блокирует ничего.

## Структура тем

```
smartwatermeter/<MAC3>/state     все показания одним JSON
smartwatermeter/<MAC3>/status    online / offline (Last Will)
smartwatermeter/<MAC3>/cmd/+     команды от Home Assistant
homeassistant/<тип>/swm<MAC3>/<объект>/config    автодискавери
```

**Базовая тема и уникальные идентификаторы строятся от MAC, а не от имени устройства.** Имя пользователь может поменять — и HA потерял бы связь с уже созданными сущностями, оставив дубликаты. Понятное имя уходит в поле `device.name` автодискавери, где его смена безопасна.

## Сущности

20 штук, все под одной карточкой устройства в HA:

| Тип | Объект | Назначение |
|-----|--------|-----------|
| sensor | `water_hot`, `water_cold` | Показания, м³. `device_class: water` + `state_class: total_increasing` |
| sensor | `temp_cold/hot/supply/return` | Температуры, °C |
| binary_sensor | `reed_hot`, `reed_cold` | Состояние герконов (диагностика) |
| sensor | `rssi`, `uptime`, `free_heap` | Диагностика |
| button | `restart`, `confirm_ota` | Управление |
| number | `debounce_closed`, `debounce_open` | Пороги антидребезга, мс |
| binary_sensor | `filter_closed` | Клапан фильтра перекрыт. `device_class: problem` — в HA «ON» подсвечивается как неисправность, а это ровно наш случай |
| binary_sensor | `filter_sensor_lost` | Датчик ХВС не отвечает (диагностика) |
| sensor | `filter_trips` | Срабатываний защиты за период |
| number | `filter_temp_on`, `filter_temp_off` | Пороги защиты фильтра, °C |

### Сущности фильтра снимаются, а не просто перестают публиковаться

Пять последних сущностей помечены в `EntityDef` флагом `filterOnly`. Если пользователь снял галочку «Home Assistant» в настройках фильтра, шаг автодискавери не пропускает их, а публикует по их темам **пустую retained-нагрузку** — это удаляет сущность из HA. Иначе в карточке навсегда осталась бы висеть недоступная сущность.

Признак берётся напрямую из `ConfigStore`, а не из `Payload`: автодискавери начинается сразу после `connect`, когда состояние ещё ни разу не публиковалось.

### Единица измерения воды — строго `m³`

Для `device_class: water` Home Assistant принимает только `m³`, `L`, `gal`, `ft³`, `CCF`. Написание `m3` он отвергает, и сущность не попадает ни в статистику, ни в панель «Вода». Ошибка тихая — в интерфейсе сущность выглядит рабочей.

### Сокращённые ключи

В payload используются `stat_t` вместо `state_topic`, `val_tpl` вместо `value_template` и так далее. HA понимает оба варианта, а на ESP с 20 КБ кучи это экономит сотни байт на каждом из 15 сообщений.

## Одна тема состояния на всё

Все сущности читают **один** JSON из `state`, каждая вытаскивает своё поле через `val_tpl`. Это одна публикация вместо пятнадцати:

```json
{
  "temperatures": {"cold": 26.3, "hot": 26.8, "supply": null, "return": 26.9},
  "meters": {"hot_m3": 10.036, "cold_m3": 1.009},
  "reed": {"hot": "OFF", "cold": "ON"},
  "sys": {"rssi": -72, "uptime": 3600, "heap": 19704},
  "cfg": {"debounce_closed": 0, "debounce_open": 0}
}
```

Отсутствующий датчик уходит как `null` — HA покажет «неизвестно», а не `-127` ([pitfalls §21](../pitfalls.md)).

## Когда публикуется состояние

- **Периодически** — раз в `mqttIntervalSec` секунд (по умолчанию 5)
- **Немедленно при импульсе счётчика** — расход воды это событие, а не фон, и ждать до пяти секунд незачем

## Публикация автодискавери разнесена по циклам

15 сообщений по ~400 байт подряд легко исчерпали бы буферы TCP на 20 КБ кучи. Поэтому описания публикуются по одному раз в `MQTT_DISCOVERY_STEP_MS` (120 мс), и только после этого начинается публикация состояния.

Сообщения `retained`: HA восстановит сущности после своего перезапуска, не дожидаясь перезагрузки устройства.

## Команды

Подписка на `smartwatermeter/<MAC3>/cmd/+`. Обработчик — `onMqttCommand()` в `Wemos_Mini.ino`:

| Команда | Действие |
|---------|----------|
| `restart` | Перезагрузка |
| `confirm_ota` | Подтверждение прошивки |
| `debounce_closed` / `debounce_open` | Порог в мс, сохраняется в EEPROM |
| `filter_temp_on` / `filter_temp_off` | Порог защиты фильтра в °C, сохраняется в EEPROM. Нижний принимается только строго ниже верхнего — иначе гистерезис схлопнется и реле начнёт дребезжать |

## Настройка

Settings → MQTT / Home Assistant: адрес брокера, порт, логин, пароль, период публикации. Пароль, как и остальные, не отдаётся клиенту — пустое поле означает «оставить прежний».

Настройки применяются после перезагрузки (как и весь `saveConfig`).

## Что проверено на тестовом брокере

| Проверка | Результат |
|---|---|
| Подключение | ✓ |
| Автодискавери | ✓ 15 сущностей, темы и payload корректны |
| Публикация состояния | ✓ раз в 5 с, `null` для отсутствующих датчиков |
| Команда `number` | ✓ `debounce_closed` 0 → 7, сохранено в EEPROM, вернулось в состоянии |
| `online` в теме status | ✓ при подключении |
| **`offline` по Last Will** | **не подтверждено** — см. ниже |

### Про Last Will

Завещание регистрируется в CONNECT-пакете (`setWill(topic, 1, true, "offline")`), и библиотека собирает пакет корректно. Но при резкой перезагрузке устройства тестовый брокер (amqtt) сообщение `offline` не опубликовал, хотя код обработки abnormal disconnect у него есть.

Причина не установлена. Проверять нужно на Mosquitto — для него это штатное поведение.

## Стоимость

| Ресурс | До MQTT | После |
|--------|---------|-------|
| RAM (статика) | 54.6% | 58.3% |
| Flash | 62.9% | 65.2% |
| Свободная куча | ~20 000 | ~19 700 |

Куча просела меньше, чем ожидалось. В момент публикации автодискавери наблюдался провал до ~14 600 — кратковременный, после завершения возвращается.
