# MeterCounter.h — Счётчики воды

## Назначение

Подсчёт импульсов герконового водосчётчика. Захват фронтов в прерывании, разбор — в `loop()`.

## Архитектура

```
ISR (CHANGE)          process() в loop()
─────────────         ──────────────────────────────
фиксирует             1. разбирает очередь событий
(время, уровень)  →   2. сверяется с уровнем пина
в кольцевой           3. проверяет созревание кандидата
                      (на момент каждого фронта, не в конце)
буфер на 32           4. переносит импульсы в показания
и выходит
```

ISR принципиально **ничего не решает**. Любая логика в прерывании означала бы потерю событий при дребезге. Буфер на 32 события переживает блокировку `loop()` чтением датчиков, отправкой почты или подключением к MQTT.

Шаг 2 — самокоррекция: если буфер всё-таки переполнился и последнее событие потерялось, автомат догоняет фактическое состояние по текущему уровню пина.

## Правила автомата

| Переход | Условие подтверждения |
|---------|----------------------|
| открыт → замкнут | LOW держится ≥ `debounceClosedMs` (по умолчанию 5 мс) |
| замкнут → открыт | HIGH держится ≥ `debounceOpenMs` (по умолчанию 50 мс) |

**Импульс засчитывается в момент подтверждённого завершения замкнутой фазы**, а не в её начале.

Каждая подтверждённая замкнутая фаза автоматически предваряется подтверждённой разомкнутой — поэтому отдельная проверка «была ли пауза» не нужна, она встроена в автомат.

## Почему считаем по завершению замыкания

Это снимает неоднозначность при пропадании питания.

Если плата выключилась с замкнутым герконом, прошлая прошивка этот импульс засчитать не могла — учёт происходит только при размыкании. Значит, после включения его можно засчитать, когда геркон разомкнётся: ни двойного счёта, ни пропуска.

При старте текущее положение геркона принимается как исходное состояние (`begin()` читает пин). Дальнейшая логика от этого не зависит.

> **При переходе со старой прошивки** возможен один лишний импульс: старая версия считала в момент замыкания, новая — в момент размыкания. Если обновление пришлось ровно на замкнутую фазу, этот литр учтётся дважды. Разовая погрешность в 1 литр.

## Залипший геркон

Счётчик может месяцами стоять с замкнутым герконом, если водой не пользуются.

- **Само залипание безопасно** — это стабильное состояние, импульс будет учтён при размыкании
- **Опасен микродребезг в залипшем положении** (вибрация трубы, ползучая струйка). Его отсекает `debounceOpenMs`: без полноценного размыкания новое замыкание не засчитывается
- **Возраст состояния считается в секундах** (`stateAgeSec`), а не через `micros()`/`millis()` — те переполняются через 71 минуту и 49 дней. Месяцы простоя отображаются корректно

В веб-интерфейсе состояние дольше суток подсвечивается красным: это либо отсутствие водоразбора, либо умерший геркон, и отличить одно от другого можно только глядя на цифру.

## Методы

| Метод | Описание |
|-------|----------|
| `begin(pin, isHot, store)` | Пин, прерывание, приём текущего положения геркона |

| `lastOpenMs()` | Длительность последней паузы |
| `queueOverflow()` | Сколько событий потеряно |

## Границы: от чего разбор зависит

Разбор сознательно не зависит от длительности импульса — кроме порогов антидребезга. Что это значит по пунктам:

| Величина | Предел | Что будет за пределом |
|----------|--------|----------------------|
| Минимальная длительность замыкания | `debounceClosedMs` (по умолчанию 5 мс) | Не импульс, а дребезг. Это и есть назначение порога |
| Минимальная пауза между импульсами | `debounceOpenMs` (по умолчанию 50 мс) | Два замыкания сливаются в одно. Отсюда потолок частоты: ~18 имп/с при значениях по умолчанию — заведомо выше любого бытового расхода |
| Максимальная длительность замыкания | нет | Импульс засчитывается при размыкании, хоть через месяц |
| Максимальная длительность паузы | нет | — |
| Пауза в работе `loop()` | нет, пока фронтов меньше 31 | См. ниже |
| Число фронтов за одну паузу `loop()` | 31 (очередь `METER_EVENT_QUEUE` минус одна ячейка) | Лишние события теряются, счётчик `queueOverflow()` растёт и показывается в Reed Diagnostics как «+N lost» |

Отсюда два следствия, которые стоит держать в голове.

**Настоящий предел — не длительность, а число фронтов.** Пока в очередь помещается вся пачка, длительность паузы `loop()` не влияет ни на счёт, ни на измеренную длительность фазы: и то и другое считается по меткам времени из ISR, а не по моменту разбора. Чистый импульс — два фронта, поэтому за одну паузу переживается 15 импульсов. Дребезжащий геркон расходует очередь быстрее.

**Переполнение micros() (каждые 71.6 минуты) безразлично.** Все сравнения идут на разностях `uint32_t`, поэтому импульс, попавший на границу, считается и измеряется верно.

Единственное место, где длительность всё-таки важна, — диагностика. Возраст состояния насыщается на ~49 сутках (`stateAgeMs()` возвращает `UINT32_MAX`). После более долгого замыкания импульс засчитывается как обычно, но его длительность известна только как «не меньше», поэтому в `min/max` она не попадает — иначе максимум навсегда застрял бы на 4.29e9 и столбец Closed ms перестал бы годиться для подбора порогов.

Всё перечисленное закреплено тестами в `test/test_meter/` — раздел «Границы».

## Настройка порогов

`debounceClosedMs` и `debounceOpenMs` лежат в EEPROM и правятся в веб-интерфейсе (Settings → Reed Debounce). Значение `0` означает «взять значения по умолчанию» (5 и 50 мс).

Поля заняли 4 байта из резерва `ConfigData` — **размер структуры не изменился**, поэтому существующие настройки читаются как есть, без сброса.

Подбирать пороги удобно по блоку Reed Diagnostics: он показывает фактические длительности замыканий (последняя, минимальная, максимальная) и счётчик дребезга.

## Единицы измерения

| Где | Единица |
|-----|---------|
| `litersPerPulseHot` / `litersPerPulseCold` | **литры** на импульс |
| Поле «L per pulse» в веб-интерфейсе | **литры** на импульс |
| `meterHotM3` / `meterColdM3` | **м³** |

```cpp
float totalM3 = (count * litersPerPulse) / 1000.0f;
```

Типовой счётчик: 1 импульс = 1 литр (1000 имп/м³). Для счётчика с ценой импульса 10 литров укажите `10`.

## Запись в EEPROM

`process()` обновляет показания только в RAM. Запись выполняется **через 30 секунд после последнего импульса** (в `loop()`).

Расход воды идёт пачками: открыли кран — закрыли. При такой политике теряется только то, что пришлось на обрыв питания прямо во время пользования, а число записей равно числу «сеансов» за сутки — десятки, а не сотни.

Периодическое сохранение раз в 5 минут осталось как подстраховка для конфигурации. Износа оно не добавляет: `EEPROM.put()` в ядре сравнивает буфер через `memcmp`, и `commit()` без изменений во flash не пишет.

## Что было сломано раньше

Старый ISR при срабатывании антидребезга делал `return`, **не записав время и не обновив состояние**:

```cpp
if (now - _lastChangeMicros < _debounceInterval) return;   // фронт потерян
```

Короткое замыкание теряло свой размыкающий фронт, флаг `_waitingForRelease` залипал в `true` — и все последующие импульсы молча пропадали:

```
t=0      FALLING → принят, pulse++, waiting=true
t=5мс    RISING  → отброшен (< 20мс), waiting остаётся true
t=1200мс FALLING → принят, но waiting==true → НЕ СЧИТАЕТСЯ
t=2400мс FALLING → снова НЕ СЧИТАЕТСЯ
```

Счётчик оживал только после замыкания длиннее 20 мс. На медленных импульсах ломалось с другой стороны: при вялом сближении магнита фронты дребезга расходились дальше 20 мс, флаг переключался туда-сюда, и один литр считался несколько раз.
